# CLAUDE.md — ifsmb.de

Website des „Institut für spontane Makespace Buildung“. Jekyll 4, GitHub Pages, Custom Domain `ifsmb.de`.

## Build

```bash
bundle exec jekyll build    # → _site/
bundle exec jekyll serve    # http://localhost:4000
ruby _scripts/check_site.rb # nach dem Build: tote Links, verwaiste Seiten, Geokoordinaten (--extern: externe Links)
ruby _scripts/check_galerien.rb # Galerien müssen Markdown sein (keine HTML-Galerien)
ruby _scripts/check_geodaten.rb # Fotos dürfen keine Geokoordinaten (EXIF-GPS/XMP) enthalten
ruby _scripts/test_formulare.rb # Formulare (➕, Todos) ↔ Vorlagen ↔ Pages CMS (.pages.yml); braucht Node
node _scripts/test_merge.js     # Dreiwege-Zusammenführung (assets/js/merge.js) für Konflikte beim direkten Bearbeiten
_scripts/test_e2e.sh            # E2E: ➕/✏️-Formulare mit GitHub-Verbindung in Headless-Chrome gegen ein Fake-GitHub (baut vorher; --no-build)
```

**E2E-Tests** (`_tests/e2e/`, Anleitung in `_tests/e2e/README.md`): `node --test` + Chrome über das DevTools-Protokoll, keine npm-Pakete (Node ≥ 22, Chrome – siehe `DEPENDENCIES.md`). Das Fake-GitHub (`_tests/e2e/lib/fake-github.js`) hält Git und Pull Requests im Speicher und hat eine Steuer-API (`/__fake/…`) für Szenarien (fremde Commits, PRs öffnen/mergen/schließen, abgelaufene Tokens, Fehler einschleusen). `assets/js/github-api.js` nimmt die Fake-Adresse aus `localStorage["ifsmb-github-api"]` nur auf `localhost`/`127.0.0.1`. Wer an `neu.js`, `formular.js`, `github-api.js`, `photo-editor.js` oder `edit-buttons.html` arbeitet, lässt sie laufen und ergänzt Szenarien; in CI läuft `.github/workflows/e2e.yml`.

Nach neuen Seiten/Posts den Link-Check laufen lassen; er läuft auch im Pages-Workflow und stoppt das Deployment bei Fehlern. Externe Links, die dauerhaft tot sind, nicht löschen, sondern in Markdown mit `{: .link-tot}` hinter dem Link markieren (`[Text](url){: .link-tot}`): Das Layout hängt 🪦 an und erklärt das Symbol unten auf der Seite; `--extern` prüft markierte Links nicht mehr. Private Repos („noch privat“) nicht markieren. Das gilt nur für Links, die früher funktioniert haben (ältere Beiträge, übernommene Texte) – einen frisch recherchierten Link, der schon beim Einfügen tot ist, einfach entfernen.

Ruby 3.1.2 (`.ruby-version`). `_site/` niemals committen.

## Sprache

Alle sichtbaren Texte sind **Deutsch**.

**Quellcode ist Englisch** – Ordner- und Dateinamen, Bezeichner (Funktionen, Variablen, CSS-Klassen, IDs, localStorage-Schlüssel, Parameter von Includes) und Code-Kommentare in Skripten, Workflows, Plugins, Layouts/Includes (Liquid- und HTML-Kommentare), CSS und JS, auch Docstrings. Neue Ordner heißen z. B. `assets/js/third-party/`, nicht `bibliotheken/`; Dokumente im Repo ebenso (`DEPENDENCIES.md`). **Nur Inhalte dürfen deutsch (oder in einer anderen Sprache) heißen:** Beiträge, Termine, Projekte, Seiten und ihre Adressen, die Ordner ihrer Bilder (`assets/images/news/<slug>/`) sowie die Felder im Front Matter, die Redakteur*innen ausfüllen (`verlinkt`, `persoenlich` …). **Dokumentation ist (vorerst) deutsch:** Der Inhalt von `CLAUDE.md`, `CHANGELOG.md`, `DATA_STRUCTURES.md`, `DEPENDENCIES.md`, READMEs und PR-Beschreibungen bleibt deutsch – nur die Dateinamen sind englisch. Später kann die Dokumentation auf Englisch umgestellt oder übersetzt werden. Ältere deutsche Namen im Code (z. B. `neu.js`, `formular.js`, `_plugins/einzeldateien.rb`, Funktionen wie `baueFelder`) nicht nebenbei umbenennen – das ist eine eigene Aufräumarbeit mit eigenem PR; neuer Code daneben bekommt trotzdem englische Namen. Deutsch bleibt alles, was Besucher*innen oder Redakteur*innen sehen: Seitentexte, Fehlermeldungen und Hilfetexte von Skripten, Namen von Workflow-Schritten, Commit-Messages und PR-Beschreibungen.

Immer **Makespace** schreiben, nie „Makerspace“. Grund: „Maker“ ist im Deutschen ein männliches Wort, und wir wollen die Gender-Diskussion vermeiden. Das gilt für alle Texte: Seiten, Posts, Projekte, Profile, Meta-Beschreibungen, Alt-Texte und Commit-Messages.

## Struktur

- `_posts/` Neuigkeiten (`/news/`)
- `_team/` Collection, ein Profil pro Datei (`/team/:name/`), Layout `member`; mit `nicht_im_team: true` bekommt eine Person eine eigene Seite unter `/team/:name/` und kann überall verlinkt werden (`team`, `author`, `owner_team`, `verlinkt`), erscheint aber nicht in der Übersicht auf `/team/`; Fremdfotos (Presse, Agentur) nur mit Erlaubnis und mit Bildnachweis in `photo_credit` (erscheint unter dem Namen)
- `_projects/` Collection (`/projekte/:name/`), Layout `project`; `status: abgeschlossen` → Archiv `/projekte/archiv/`; `status: idee` = Projektidee (eigener Abschnitt „Ideen“, nicht auf der Startseite); `status: anfrage` = eingegangene Anfrage, die vielleicht ein Projekt wird (eigener Abschnitt „Anfragen“, nicht auf der Startseite). **Teilprojekte:** `teil_von: [<Dateiname des übergeordneten Projekts>, …]` (z. B. `[3d-druck-ag-ktg]`; ein einzelner Name ohne Liste geht auch) – ein Teilprojekt kann zu mehreren Projekten gehören und erscheint dann auf jeder Elternseite unter „Teilprojekte“, aber nicht in den Übersichten (Startseite, `/projekte/`, Archiv); sie zeigen oben und unten „Dieses Projekt ist ein Teil von: …“. **Verwandte Projekte:** `verwandt: [<Dateiname>, …]` zeigt unten Buttons „Verwandte Projekte“ – in beide Richtungen, ein Eintrag bei einem der Projekte reicht; und haben ein eigenes `event_tag`. `start` muss immer ein Datum sein (wird zum Sortieren genutzt), `event_tag` ein eigenes Stichwort – nie ein allgemeines wie `35services`, sonst landen alle Beiträge dazu auf der Projektseite; `event_tag: ktg` listet alle Termine und Posts mit `tags: [ktg]` auf der Projektseite, und die Terminseite verlinkt zurück aufs Projekt. Fortschritt bevorzugt als **kleine Beiträge** (Posts mit dem `event_tag` des Projekts in `tags`, persönliche mit `persoenlich: true`; mit `nur_projekt: true` erscheint ein Beitrag nicht unter Neuigkeiten, auf der Startseite und im RSS-Feed, sondern nur auf der Projektseite) – so kann jede*r Beteiligte eigene Updates schreiben. Fotos und Videos dürfen auch direkt auf die Projektseite (als Markdown-Galerie im Text, siehe „Bilder und Videos“), vor allem bei einfachen Projekten mit wenigen Bildern; zeigen sie einen bestimmten Fortschritt oder Tag, lieber als Beitrag. Kurze Notizen ohne eigenen Beitrag als `updates:` (Liste aus `datum` und `text` in Markdown, ohne Liquid). Die Projektseite mischt beides zu „Stand / Updates“ (neuestes zuerst, mit Autor*in); „Letztes Update“ im Kopf und auf der Projektkarte kommt aus `_includes/projekt-letztes-update.html`; Projektkarten in den Übersichten kommen aus `_includes/projekt-karte.html` und zeigen mit `_includes/projekt-aktivitaet.html` Symbole mit hochgestellten Zahlen (Teilprojekte, Termine, Updates, Geräte, Beteiligte) als Direktlinks in die Projektseite; Beiträge zeigen oben „Update zum Projekt …“
- `_herausforderungen/` Collection (`/herausforderungen/:name/`), Layout `herausforderung`: Aufgaben, Probleme und offene Fragen – kleiner als ein Projekt; **ein Projekt hat viele Herausforderungen**. Felder: `art` (`aufgabe`/`problem`/`frage`), `status` (`offen` – Standard, `in-arbeit`, `geloest`), `seit`, `geloest_am`, `loesung` (Markdown, erscheint unter „Lösung“), `team` (Zuständige, eine oder mehrere Personen), `projekte` (Projekt-Dateinamen; alternativ `tags` mit dem `event_tag` des Projekts), `verlinkt` (Termine, Geräte, Beiträge, Partnerseiten …), `persoenlich: true` (aus privaten Projekten: eigener Abschnitt auf der Übersicht). Projektseiten zeigen ihre Herausforderungen als Karten (`#herausforderungen`, offene zuerst), Projektkarten zählen offene mit 🧗, Teamprofile listen die eigenen; sonst erscheinen sie unten bei „Verbindungen“. Karte und Status kommen aus `_includes/herausforderung-karte.html` und `_includes/herausforderung-status.html`. Offene Fragen in Projekttexten („Welche Teile fehlen?“) lieber als Herausforderung anlegen statt als Teilprojekt.
- `_data/partners.yml` Partnerliste – neue Partner gehen auch als eigene Datei `_data/partner/<name>.yml` (gleiche Felder, ein Partner pro Datei; `_plugins/einzeldateien.rb` hängt sie an die Liste an, „➕ Partner“ auf `/partner/` legt so eine Datei an); `logo_dark: true` für helle Logos; `page: /partner/<name>/` verlinkt eine eigene Partnerseite (`partner/<name>/index.md`); die Partnerübersicht listet automatisch alle Projekte, deren `partners:` den Namen enthält (persönliche mit Hinweis), und die Geräte mit `owner_partner`
- `_events/` Kalender-Termine (`/kalender/:name/`), Layout `event`; Felder `start`, `end`, `all_day`, `location`, `location_url`, `summary`, `team` (Team-Kürzel der Leute, die dabei sind/waren → Teamprofil „Termine“, nur eintragen, wer wirklich da war), optional `gallery` (Liste aus `image`, `thumb`, `alt`; Bilder unter `assets/images/kalender/<termin>/`, Originale in `_logo/kalender/` – nicht committet) `date_label` (Text statt Datum, wenn der Tag noch nicht feststeht – iCal macht daraus einen ganztägigen Termin am Ersten des `start`-Monats mit „TBD: “ vor dem Titel) `projekte` (Liste von Projekt-Dateinamen – zusätzlich zu Projekten, deren `event_tag` in `tags` steht), `partners` (Namen aus `_data/partners.yml`, erscheinen auf `/partner/`), `persoenlich: true` (private Termine aus dem Team, brauchen `team`: nie auf Startseite, in `/kalender/` oder im iCal-Feed, nur im Teamprofil und auf der Terminseite mit Hinweis „kein Termin des Instituts“) und `nur_projekt: true` (interne Termine, z. B. Ausflüge der KTG-AG: solange sie bevorstehen, nicht auf der Startseite, im Kalender und im iCal-Feed, nur auf der Projektseite über das Stichwort und auf der Terminseite selbst; danach ganz normal unter „Vergangene Termine“ – der Kalender wird bei jedem Build neu berechnet)
- `_data/slogans.yml` wechselnde Slogans auf der Startseite (`text`: jede Zeile eine Zeile auf der Seite, `**fett**` = gelb hervorgehoben; der erste steht ohne JavaScript da) – neue Slogans einfach unten anhängen, auch in Pages CMS; Besucher*innen schlagen welche über `{% include slogan-editor.html %}` vor (Beitrag „Slogans gesucht“), die Datei liegt dafür unter `/source/_data/slogans.yml`
- `kalender.ics` erzeugt den iCal-Feed. Die Datei enthält echte CRLF-Zeilenenden (RFC 5545) – nur mit Werkzeugen bearbeiten, die `\r\n` erhalten (`.gitattributes`: `-text`). Lange Zeilen bricht `_includes/ics-line.txt` um. Kopf und VEVENT stehen in `_includes/ics-kopf.txt` und `_includes/ics-vevent.txt`; dieselben Bausteine nutzt `_plugins/termin_ics.rb`, das pro Termin eine eigene Datei `/kalender/<termin>.ics` erzeugt und pro Projekt, Teamprofil und Partnerseite einen Feed mit allen Terminen, auch vergangenen (`/projekte/<name>.ics`, `/team/<name>.ics`, `/partner/<name>.ics`). Die Buttons dazu („📅 In den Kalender“ auf der Terminseite, „📅 Abonnieren“ neben der Termine-Überschrift auf `/kalender/`, Projekt, Teamprofil, Partnerseite) kommen aus `_includes/kalender-abo.html`: ein Fenster (`<dialog id="abonnieren">`, Skript `assets/js/abo.js`, ohne JS ein normaler Link zur `.ics`) mit „Apple Kalender & Outlook“ (`webcal://` bzw. die `.ics` eines Termins), „Google Kalender“ (Abo-Link `calendar.google.com/calendar/render?cid=webcal://…` bzw. ausgefülltes Formular `action=TEMPLATE`) und Download. Ein Kalender-Fenster pro Seite; `<seite>#abonnieren` öffnet es direkt. Welche Termine dazugehören, entscheidet `_includes/termine-auswahl.html` – für Seite und Feed gleich.
- **RSS-/Atom-Feeds**: `/feed.xml` (Neuigkeiten des Instituts, ohne `persoenlich`/`nur_projekt`) und aus `_plugins/beitrag_feeds.rb` pro Projekt `/projekte/<name>/feed.xml` (Beiträge mit dem `event_tag` plus die `updates:` – wie „Stand / Updates“), pro Person `/team/<name>/feed.xml` (alle Beiträge mit ihr als `author`, auch persönliche) und `/news/persoenlich/feed.xml`. Alle Feeds nutzen `_includes/atom-feed.xml`, die Auswahl für Projekte/Personen steht in `_includes/feed-auswahl.html` (für Seite und Feed gleich). Die Buttons „📡 RSS-Feed“ (auf `/news/`, `/news/persoenlich/`, neben „Stand / Updates“ auf Projektseiten, im Kopf des Teamprofils) kommen aus `_includes/feed-abo.html`: ein Fenster wie beim Kalender (`<dialog id="rss">`, `<seite>#rss` öffnet es) mit Feed-Adresse zum Kopieren, „Im Feed-Reader öffnen“ (`feed:`), Feedly und Inoreader.
- `_press/` Pressemitteilungen (`/presse/:slug/`), Layout `press`; Kurzprofil & Pressekontakt in `_data/presse.yml`, Downloads in `_data/pressematerial.yml`, Berichte anderer über uns („Wir in der Presse“) in `_data/presseberichte.yml` oder als eigene Datei `_data/pressebericht/<name>.yml` (wird nach `datum` einsortiert; „➕ Wir in der Presse“ auf `/presse/`)
- Posts mit `original_url` / `original_site` / `author` (Team-Kürzel) zeigen automatisch den Hinweis „Ursprünglich veröffentlicht von … auf …“
- `_equipment/` Ausstattung (`/ausstattung/:name/`), Layout `equipment`. Das Institut besitzt (noch) nichts: jedes Gerät hat mindestens einen Besitz-Eintrag: `owner_partner` (Namen aus `_data/partners.yml`), `owner_team` (Team-Kürzel), `owner_name` (freie Namen) – jeweils ein Wert oder eine Liste, kombinierbar (mehrere Besitzer*innen). Besitz und Standort sind besondere Verbindungen: eigene Gruppen „Gehört“/„Standort“ unten auf der Geräteseite, eigene Linien im Netzwerk (`/netzwerk/`); `standort` ohne `standort_partner` wird dort ein eigener Ort. `status:` `in-aussicht` (kommt vielleicht), `in-reparatur`, `im-test`. Standort mit `standort` (Text) und optional `standort_partner` (Partnername → Link). Weitere Fotos als `gallery` (Liste aus `image`, `thumb`, `alt`), Videos als `videos` (Liste aus `src`, `poster`, `caption`). Neuigkeiten zum Gerät (Umbauten, Erfahrungen, Reparaturen) als `updates:` (Liste aus `datum` und `text` in Markdown, Fotos darin als Markdown-Galerie mit `{: .gallery}`) – erscheinen als „Stand / Updates“ auf der Geräteseite (neuestes zuerst), „Letztes Update“ steht im Kopf. Die Übersicht `/ausstattung/` gruppiert automatisch nach `kategorie` (enthält „3D-Drucker“ / „3D-Scanner“ / Rest). Ohne freies Foto: eigene SVG-Illustration mit `image_is_illustration: true` – keine Hersteller- oder Shopfotos übernehmen (Urheberrecht). Partnerseite und Teamprofil listen die Geräte automatisch.
- **Stichworte (`tags`)** verknüpfen alles miteinander: Posts, Termine, Ausstattung, Pressemitteilungen tragen `tags: [...]`, Projekte ihr `event_tag`. `_includes/verknuepft.html` zeigt auf jeder Seite alles mit gemeinsamen Stichworten, `/stichworte/` listet alle. Anzeigenamen in `_data/stichworte.yml`. Sehr allgemeine Stichworte (`_data/stichworte_breit.yml`: `ktg`, `35services`, `3d-drucker`) werden auf Geräteseiten für „Verknüpft“ ignoriert, wenn das Gerät eigene Stichworte hat.
- Stichwort-Konventionen: Kleinbuchstaben mit Bindestrich. Projekt-Ort (`ktg`, `rosalind-franklin-gym`), Herkunft (`35services` für alle von 35services.de übernommenen Beiträge), Besitzer*in eines Geräts (`35services`, `bietenholz`), Gerät (`bambu-lab-a1-mini`, `waermebildkamera`, `u1` für den Snapmaker U1 …), Gerätetyp (`3d-drucker`).
- `/projekte/ideen/` (`projekte/ideen.md`): Linksammlung mit Projektideen; ✅ = schon gebaut. Links immer ohne Tracking-Parameter (`?si=`, `?is=`, `&pp=`, `spm=` …).
- `/angebot/`: Angebote und „Warum ein Institut?“
- **Persönliche Beiträge und Projekte** (`persoenlich: true`): private Makespace-Updates aus dem Team. Sie erscheinen **nicht** in den Listen des Instituts (Neuigkeiten, Startseite, RSS, Projekte, Archiv), sondern im Teamprofil („Persönliche Projekte“, „Persönlicher Blog“) und auf `/projekte/persoenlich/` bzw. `/news/persoenlich/` (unten auf den Listenseiten verlinkt). Posts brauchen `author` (ein Team-Kürzel oder eine Liste bei mehreren Autor*innen – der Beitrag erscheint dann in jedem persönlichen Blog), Projekte die Person unter `team`. Die Seiten tragen den Hinweis „kein Beitrag/Projekt des Instituts“.
- Navigation steht in `_config.yml` unter `nav`; Einträge mit `children` werden zu einem Untermenü (z. B. „Wir“ mit Projekte, Angebot, Ausstattung, Team)
- `future: true` in `_config.yml`, sonst baut Jekyll Termine mit Datum in der Zukunft nicht
- **Suche** `/suche/` mit Pagefind: Index entsteht erst nach `jekyll build` im Workflow `.github/workflows/pages.yml` (`npx pagefind --site _site`; Pages-Source = „GitHub Actions“). Indexiert wird alles im `data-pagefind-body`-Wrapper aus `_layouts/default.html`, Filter „Bereich“/„Stichwort“ aus `_includes/suche-meta.html`. Reine Übersichtsseiten bekommen `suche: false`. Pagefind-Version im README und Workflow gleich halten. **Suchindex zum Finden von Erwähnungen nutzen:** Um bei neuen Personen, Projekten, Geräten oder Themen alle passenden Stellen auf der Website zu finden (und nichts zu übersehen, z. B. abweichende Schreibweisen oder Übersichtsseiten wie `/spenden/`), den lokalen Server starten, den Pagefind-Index mit `npx -y pagefind@1.5.2 --site _site` bauen und direkt per Node abfragen (`const pf = await import("./_site/pagefind/pagefind.js"); await pf.options({ basePath: "http://127.0.0.1:<port>/pagefind/" }); await pf.init(); const res = await pf.search("Suchbegriff");`), zusätzlich zu `todos/suchindex.json`.
- **Bearbeiten-Button**: `_layouts/default.html` zeigt unter jeder Seite einen Button „✏️ `<page.path>`“ (der Pfad der Quelldatei) → GitHub-Editor für `page.path` (Repo/Branch in `_config.yml` unter `repository`/`branch`)
- **Neu-Buttons**: In derselben Zeile wie der Bearbeiten-Button stehen ➕-Buttons (`_includes/neu-buttons.html`), die den GitHub-Editor für eine neue Datei öffnen (`/new/<branch>/<ordner>?filename=…&value=…`) – mit einer Vorlage aus `_includes/vorlagen/` (Beitrag, Termin, Projekt, vergangenes Projekt fürs Archiv, Gerät, Herausforderung, Teamprofil, Pressemitteilung, Partner, Pressebericht), die alle Felder mit Kommentar enthält und die Verbindung zur aktuellen Seite schon eingetragen hat (Teamprofil → `author`/`team`/`owner_team`, Projekt → `event_tag`/`teil_von`, Partnerseite → `partners`/`owner_partner`, Termin/Gerät/Beitrag → `tags` + `verlinkt`, Projekt/Termin/Teamprofil → Herausforderung mit `projekte`/`team`; Übersichtsseiten → leere Vorlage; `/projekte/archiv/` → vergangenes Projekt mit `status: abgeschlossen` und Gliederung für den Rückblick). `teil_von` bleibt in den Vorlagen leer (nil), sonst verschwindet ein Projekt aus den Übersichten – die filtern auf `teil_von == nil`. `JJJJ-MM-TT`, `JJJJ` und `TZTZ` ersetzt ein kleines Skript beim Klick durch das heutige Datum. **Ein normaler Klick öffnet stattdessen ein Formular auf der Seite** (`assets/js/neu.js`, erst beim Klick geladen; Strg/⌘-Klick und „Vorlage mit allen Feldern ↗“ öffnen weiter GitHub direkt): Felder mit Auswahllisten und Autovervollständigung, Live-Vorschau der Datei, Entwurf im localStorage, „Auf GitHub anlegen“ kopiert die Datei und öffnet den GitHub-Editor mit dem fertigen Inhalt. Jeder Typ ist ein Schema in `TYPEN` (`neu.js`); die Verbindung zur Seite kommt aus `data-neu` (`_includes/neu-button.html`). Bausteine, die auch der Todo-Editor nutzt (Dialog, Chip-Felder mit Autovervollständigung, Personen-Avatare, YAML, GitHub-Schritt), stehen in `assets/js/formular.js`; Konfiguration und Skript-Lader in `_includes/formular-config.html` (in jeder Seite), Daten aus `todos/suchindex.json` (Personen, Projekte, Stichworte, Partner, Gerätekategorien, Seiten). **Neues Feld oder neuer Typ:** Schema in `neu.js`, Vorlage in `_includes/vorlagen/` und `.pages.yml` gemeinsam ändern – `ruby _scripts/test_formulare.rb` (läuft in „Prüfen“ und „Pages“) prüft, dass jede Datei, die ein Formular schreibt, als YAML lesbar ist, nur Felder der Vorlage nutzt und zu Pages CMS passt (Ordner, Dateiname, Listen vs. Einzelwerte, Auswahlwerte, Datumsformat), und dass Todo-Dateien beim Lesen und Schreiben gleich bleiben. Felder mit `list: true` in `.pages.yml` schreibt das Formular immer als Liste. **✏️-Button** (`_includes/edit-buttons.html`, links in der Bearbeiten-Zeile, nur das Symbol; „Bearbeiten“ steht als Tooltip und für Screenreader drin) öffnet auf Seiten der Sammlungen posts, events, projects, equipment, herausforderungen, team und press dasselbe Formular mit den Werten der Seite: `NeuFormular.edit` (`neu.js`) lädt die unverarbeitete Quelle von `/source/<pfad>` (`_plugins/source_files.rb` kopiert sie nach dem Build, eigene Domain, keine Anfrage an GitHub), liest das Front Matter mit `Formular.splitFile`/`yamlValue` (`formular.js`) und schreibt **nur geänderte Felder** neu – unbekannte Felder (Galerien, Links), Kommentare und Formatierung bleiben Byte für Byte; abgeleitete Felder (Dateiname, event_tag, Ende …) folgen beim Bearbeiten nicht. Die Vorschau markiert geänderte Zeilen. Speichern: GitHubs Edit-Seite lässt sich nicht vorbefüllen, daher kopieren → Editor öffnen → alles markieren und einfügen → PR. Strg/⌘-Klick und Seiten ohne Formular: direkt GitHubs Editor. Daneben das GitHub-Logo mit dem Dateipfad → Datei auf GitHub (`/blob/`). `_scripts/edit_examples.js` + `test_formulare.rb` prüfen jede echte Seite: ohne Änderung bytegleich, nach Änderung von Titel, Liste und Text liest Jekyll die neuen Werte und alle anderen Felder unverändert.
- **Direkt bearbeiten (Prototyp):** Mit „🔑 GitHub verbinden“ (Fine-grained Token, `assets/js/github-api.js`) legen die ➕/✏️-Formulare Pull Requests selbst an – Datei und Fotos in einem Commit auf einem Branch `web/…`, nie direkt auf `main`. Fotos laufen durch `assets/js/photo-editor.js` (drehen, zuschneiden, verpixeln, Alt-Text, 1600 px + `-600w`, ohne Metadaten) und werden im Formular einer Verwendung zugeordnet (`direct.slots()` in `neu.js`, abgeleitet aus den Feldern des Typs: Galerie im Text, `image`, `photo`, `logo`, `social_media_preview_image` → `NN-social.jpg` 1200 × 630); nur verwendete Fotos werden hochgeladen. `<seite>#bearbeiten` öffnet das ✏️-Formular; mit GitHub-Verbindung warnt es vor offenen PRs zur selben Datei und kann dort weiterarbeiten. **Konflikte** löst das Formular selbst: vor jedem Commit wird das Ziel (main oder PR-Branch) neu gelesen und mit `assets/js/merge.js` zusammengeführt (Front Matter pro Feld, Listen als Mengen, Text zeilenweise); Überschneidungen zeigt eine Konfliktbox mit Wahl. - **Todos** `/todos/` – getrennt von den Herausforderungen: **Herausforderungen** (`_herausforderungen/`, `/herausforderungen/`) sind die Bestandsaufnahme (sammeln und dokumentieren), **Todos** das, was jemand konkret anpackt und verfolgt. Todos: eine Markdown-Datei pro Person `todos/todo-<team-kürzel>.md` (ohne Front Matter → statische Datei, wird von `assets/js/todos.js` erst bei Bedarf geladen). Aufbau: `## <Feld>` = Eisenhower-Feld (🔥 Sofort erledigen, 📌 Einplanen, 🤝 Abgeben, 💤 Später, ✅ Erledigt), `### <Titel> {#id}` = eine Herausforderung (Reihenfolge = Priorität), direkt darunter ein `yaml`-Block (`kurz`, `art`, `status`, `seit`, `faellig`, `geloest_am`, `helfer` = helfende Hände als Team-Kürzel, `projekte`, `tags`, `verlinkt`), danach freier Markdown-Text ohne `##`/`###`. Die Person der Datei ist hauptzuständig. Bearbeitet wird im Browser (localStorage, sofort gespeichert); gespeichert wird per Diff → Kopieren → GitHub-Editor (Pull Request). Die Autovervollständigung nutzt `todos/suchindex.json` (von Jekyll erzeugt) und zusätzlich Pagefind, wo es gebaut ist. Format-Funktionen `TodoFormat.parse`/`serialize` laufen auch in Node (`require("./assets/js/todos.js")`). Projektseiten und Teamprofile haben unter „Todos“ einen Button (`_includes/todos-knopf.html`), der `todos.js` erst beim Klick lädt und das Fenster direkt auf der Seite öffnet – auf Projektseiten nur mit den Todos des Projekts (`projekte` oder `event_tag` in `tags`) von allen Personen; ➕ trägt das Projekt schon ein. Konfiguration für beide aus `_includes/todos-config.html`. `#…` auf `/todos/` ist eine Route der App; der Link-Check prüft dort keine Anker. Im Netzwerk lädt `assets/js/netzwerk.js` die Todo-Dateien vor dem Start (Liste in `#netz-todos`, Parser `TodoFormat` aus `todos.js`): Knoten `todo` (ID `todo:<person>/<id>`), Kante „gehört“ zur Person der Datei, normale Kanten zu `helfer`, `projekte`, `tags`→Projekt und `verlinkt`; Herausforderungen und Todos sind kleine Knoten.

- **Gelesen-Markierung**: Jede Inhaltsseite hat im Front Matter eine `uuid` (zufällige UUID v4, nie ändern oder kopieren – gilt auch, wenn die Datei umzieht). `_layouts/default.html` schreibt sie in `<body data-uuid>`, `assets/js/gelesen.js` merkt sich beim Öffnen `gelesen_<uuid>` in localStorage und hängt an alle Links im Inhalt zu gelesenen Seiten ein ✓ (über `/gelesen.json`, URL → uuid; Links mit `#abschnitt` zählen nicht). Neue Seiten bekommen die uuid aus dem Formular/der Vorlage (`UUID-NEU` wird beim Klick ersetzt); sonst `ruby _scripts/uuids_ergaenzen.rb` (ergänzt fehlende; `--pruefen` lässt Workflows bei doppelten uuids scheitern). Übersichtsseiten (`suche: false`) und Weiterleitungen bekommen keine uuid. Beschrieben im Impressum unter Datenschutz.

- **Badges zum 3D-Druck** (`_data/badges.yml`): Logo-Badge und Badges mit Namen, Dateien in `assets/badge/` (3MF/OBJ/STL/Vorschau, erzeugt mit `_logo/badge/export_colored.py`, siehe `_logo/badge/README.md`). `/presse/#badge` zeigt alle, das Teamprofil das Badge mit passendem `team`. `_includes/badge-3d.html` = drehbares 3D-Modell + Downloads; `assets/js/badge3d.js` (WebGL, ohne Bibliothek) lädt das OBJ, ohne JS/WebGL bleibt das Vorschaubild.
- **Karte** `/karte/` (`karte/index.html` + `assets/js/karte.js`, ohne Bibliothek): zeigt die Orte aus `_data/orte.yml` (`id`, `name`, `adresse`, `lat`, `lon`, optional `partner`, `finden`, `fern`, `ungefaehr`) auf OpenStreetMap. Projekte, Termine und Geräte landen automatisch an einem Ort, wenn ihr `ort`/`location`/`standort` eines der `finden`-Wörter enthält, sonst über `standort_partner`/`partners`/`owner_partner` = `partner` des Orts. Beiträge erscheinen beim Ort ihres Projekts (über `tags`/`projekte`). Mit `orte: [<id>]` lässt sich jede Seite fest einem Ort zuordnen. Neue Orte: Koordinaten auf openstreetmap.org nachsehen, nur öffentliche Adressen (Schulen, Vereine, Veranstaltungsorte) – nie Wohnadressen; Werkstätten von Privatleuten nur straßengenau mit `ungefaehr: true`. Kommende Termine sind im Ortspanel markiert.

- **Gelöschte Seiten weiterleiten**: Wird eine Seite gelöscht, die schon live war, an ihrer alten Adresse eine Weiterleitung anlegen – Datei mit `layout: weiterleitung`, `permalink: <alte Adresse>`, `ziel: <neue Adresse>` (optional `ziel_titel`), z. ## Konventionen

- Kein CSS-/JS-Framework, alle Styles in `assets/css/style.css` mit CSS-Variablen
- Keine externen Ressourcen (Fonts, Skripte, Tracker) einbinden – Datenschutzhinweis im Impressum verspricht das. Einzige Ausnahme: die Kartenbilder von OpenStreetMap auf `/karte/`, und nur nach Klick auf „Karte laden“ (im Impressum unter Datenschutz beschrieben)
- Fremde Bibliotheken, Werkzeuge und andere Abhängigkeiten: siehe Abschnitt **„Abhängigkeiten“** unten und `DEPENDENCIES.md`. Bisher im Browser: OverType (Markdown-Editor der Formulare) – `neu.js` macht daraus die Felder mit `markdown: true`; Werkzeugleiste mit 🛠️ ein-/ausblendbar, auf dem Handy anfangs aus, Wahl im localStorage (`ifsmb-md-toolbar`); zusätzlich zu OverTypes Kürzeln Durchgestrichen (⇧⌘X) und Unterstrichen (⌘U → `<u>…</u>`) als eigene Knöpfe/Tasten in `neu.js` (`toolbarButtons`, `onEditorKeydown`). Alle Kürzel erklärt der Beitrag `_posts/2026-11-17-mitschreiben-leicht-gemacht.md` – bei Änderungen dort mitpflegen
- **E-Mail-Adressen immer maskieren, nie im Klartext** – weder in HTML/Markdown noch in `_data/*.yml`, Front Matter, `.pages.yml`-Beispielen, Alt-Texten oder `mailto:`-Links. Einzig erlaubt: das `.obf-mail`-Muster (siehe README) mit base64 in `data-em` (`printf 'name@domain.de' | base64`) und maskiertem Anzeigetext „name [at] domain [punkt] de“; in Datendateien das passende `*_b64`-Feld (z. B. `kontakt_email_b64`) plus maskierte Anzeige. Telefonnummern genauso über `.obf-tel` (siehe README)
- Original-Logos in `_logo/`, `_logo/README.md` aktuell halten
- Platzhalter sind mit `<span class="todo">` markiert
- **Bilder und Videos als Markdown** (Plugin `_plugins/galerie.rb`, läuft im eigenen Pages-Workflow): Bilder direkt untereinander, ohne Leerzeile, darunter `{: .gallery}`:
  ```markdown
  ![Alt-Text 1](/assets/images/news/<slug>/01.jpg)
  ![Alt-Text 2](/assets/images/news/<slug>/02.jpg)
  {: .gallery}
  ```
  Das Plugin baut daraus `<div class="gallery">` mit `a.lightbox` und nimmt automatisch das Vorschaubild `NN-600w.jpg`, wenn es existiert. Ein einzelnes Bild wird automatisch groß (`gallery-single`), kleine Vorschaubilder mit `{: .gallery .gallery-small}`. Jedes Bild braucht einen Alt-Text, sonst bricht der Build ab. Videos: `![Kurze Beschreibung](/assets/video/…/01.mp4)` als eigener Absatz wird zum `<video class="post-video">` mit `01.jpg` als Vorschaubild. Kein HTML für Galerien mehr schreiben – `_scripts/check_galerien.rb` meldet HTML-Galerien (`div.gallery`, `a.lightbox`, WordPress-Galerien) mit Datei und Zeile; der Workflow `.github/workflows/pruefen.yml` lässt damit jeden Pull Request durchfallen, `pages.yml` stoppt das Deployment.
- Keine externen Einbettungen (YouTube-iframes, fremde Videos/Bilder): Videos lokal als 720p-MP4 in `assets/video/`, YouTube nur als Link mit lokalem Vorschaubild
- **Fotos niemals mit Geokoordinaten hochladen oder veröffentlichen**: Fotos immer ohne Metadaten ausliefern (Handyfotos enthalten GPS-Koordinaten) – vor dem Ablegen unter `assets/` immer mit Pillow ohne EXIF-/XMP-Metadaten neu speichern, Originale von Personenfotos nicht committen. `_scripts/check_geodaten.rb` (wird auch von `check_site.rb`, `pruefen.yml` und `pages.yml` ausgeführt) prüft alle Bilder auf EXIF-GPS- und XMP-Geodaten und bricht den Build bzw. das Deployment ab, sobald Koordinaten enthalten sind.
- Fotos mit Kindern: Gesichter (auch Profile und Hinterköpfe) unkenntlich machen, bevor sie auf die Seite kommen. Die macOS-Vision-Gesichtserkennung findet nicht alle Gesichter – Ergebnis immer selbst in voller Größe prüfen und fehlende Köpfe von Hand ergänzen. Originale bleiben in `_logo/news/`, `_logo/kalender/`, `_logo/team/` (in `.gitignore`)

## Beiträge von 35services.de übernehmen

Falko schreibt Beiträge zuerst auf https://35services.de. Soll ein Beitrag hier erscheinen, gilt dieses Muster:

1. **Datum & Titel** aus der WordPress-API holen (genaue Veröffentlichungszeit):
   `curl -s "https://35services.de/wp-json/wp/v2/posts?slug=<slug>&_fields=slug,date,title"`
   → Datei `_posts/<YYYY-MM-DD>-<slug>.md`, `date: <YYYY-MM-DD HH:MM:SS> +0100/+0200` (MEZ/MESZ beachten)
2. **Front Matter**:
   ```yaml
   title: "<Titel wie im Original>"
   date: 2026-05-25 14:37:44 +0200
   author: falko-richter
   original_url: https://35services.de/<jahr>/<slug>/
   original_site: 35services.de
   ```
   Zusätzlich immer `tags: [35services]` setzen (plus Stichworte für erwähnte Geräte/Projekte).
   Das Layout `post` zeigt daraus oben automatisch „Ursprünglich veröffentlicht von Falko Richter auf 35services.de“ mit Link.
3. **Text** wörtlich übernehmen (Absätze, Listen, Links als Markdown). Einzige Änderung: „Makerspace“ → „Makespace“. E-Mail-Adressen nur in der schon verschleierten Form des Originals („falko [at] 35services [punkt] de“) oder per `.obf-mail`.
4. **Bilder** lokal speichern, nie von 35services.de einbinden: größte Version laden, mit Pillow ohne Metadaten neu speichern als `assets/images/news/<slug>/NN.jpg` (max. 1600 px) und `NN-600w.jpg`; einbinden als Markdown-Galerie (Bilder untereinander, darunter `{: .gallery}`, auch für ein Einzelbild). Aussagekräftige Alt-Texte, Screenshots beschreiben.
5. **Videos** (`wp-block-video`, oft 4K oder `.mov`) mit ffmpeg auf 720p verkleinern (`-crf 28 -preset slow -movflags +faststart -map_metadata -1`) nach `assets/video/news/<slug>/NN.mp4` plus Vorschaubild `NN.jpg`; einbinden als `![Beschreibung](/assets/video/news/<slug>/NN.mp4)` (eigener Absatz) an der Stelle wie im Original.
6. **YouTube** nie als iframe: Vorschaubild `img.youtube.com/vi/<id>/hqdefault.jpg` lokal speichern und als `<a class="video-link">` auf youtube.com verlinken.
7. Danach `bundle exec jekyll build`, Seite ansehen, Größe von `assets/` im Blick behalten.

## Durchsicht vor dem Push

- **Viele Änderungen auf einmal** (mehr als 2 betroffene Seiten/Ressourcen, z. B. mehrere Beiträge, Termine und Profile aus einer Nachricht): erst eine Durchsicht `_review.md` im Projektordner schreiben und **nicht pushen**, bis sie durchgesehen ist. Darin pro Änderung: was sich ändert, Link zur lokalen Seite, Annahmen und offene Fragen. Antworten werden direkt in die Datei geschrieben; nach dem Einarbeiten die Datei löschen. `_review.md` steht in `.gitignore` und wird nie committet.
- **Worktree live ansehen**: Wer in einem lokalen Worktree arbeitet (`.claude/worktrees/<name>/`), startet dort im Hintergrund einen eigenen Server, sobald es etwas zu sehen gibt – auf dem nächsten freien Port ab 4001 (Port 4000 gehört dem Haupt-Checkout; frei prüfen mit `lsof -nP -iTCP:<port> -sTCP:LISTEN`): `bundle exec jekyll serve --port <port>`. Die Adresse (`http://localhost:<port>/`) kommt mit klickbaren Links auf die geänderten Seiten in `_review.md` (im Worktree-Ordner) und in den Abschlussbericht, damit alles live angesehen werden kann; Port 4000 nur auf ausdrücklichen Wunsch auf den Worktree umstellen. Server laufen lassen, bis die Änderung gemergt oder verworfen ist.
- **Inline-Links auch semantisch verbinden**: Verlinkt ein Text eine andere Seite der Website (Projekt, Termin, Beitrag, Person, Gerät, Partner- oder normale Seite), die Verbindung zusätzlich im Front Matter eintragen (Ausnahme: `/netzwerk/` – dazu gehört ohnehin alles) – über das passende Feld (`tags`/`event_tag`, `team`, `partners`, `teil_von` …) oder sonst `verlinkt`. Dann erscheint sie unten bei „Verbindungen“ und im Netzwerk.
- **Inhaltsseiten in Markdown**: Texte als `.md` schreiben, HTML nur für Bausteine, die Markdown nicht kann (Karten-Raster, Hinweisboxen, verschleierte E-Mail) – darin mit `markdown="1"` weiter Markdown. Überschriften-Anker explizit setzen (`{: #anker}`), wenn andere Seiten darauf verlinken. Reine Listen-/Übersichtsseiten mit viel Liquid (Startseite, Kalender, Projekte …) bleiben HTML.
- **Links in Markdown immer klickbar**: als `[Text](URL)` schreiben, nie als nackte URL – das gilt für `_review.md`, Feedback-Dateien, PR-Beschreibungen und alle Inhalte.

## Changelog

`CHANGELOG.md` folgt [Keep a Changelog](https://keepachangelog.com/de/1.0.0/), auf Deutsch. **Nur Funktionen der Website kommen hinein** – neue oder geänderte Layouts, Includes, Plugins, Seitentypen und Felder, Skripte, Workflows, CSS/JS, Regeln für die Arbeit am Repo, behobene Fehler. **Keine Inhalte**: neue oder geänderte Beiträge, Termine, Projekte, Teamprofile, Geräte, Partner, Pressemitteilungen, Textseiten und Fotos bekommen keinen Eintrag – was wann dazukam, zeigen das Netzwerk und seine Zeitleiste (`/netzwerk/`). Jede nennenswerte Funktionsänderung kommt mit in den Commit: zuerst unter `## [Unreleased]`, sortiert nach `### Hinzugefügt`, `### Geändert`, `### Veraltet`, `### Entfernt`, `### Behoben`, `### Sicherheit`. Die Seite hat keine Versionsnummern: Beim Push nach `main` wird `[Unreleased]` zum Tagesabschnitt `## [JJJJ-MM-TT]` (neueste oben, Vergleichslinks unten pflegen). Einträge für Menschen schreiben, nicht Commit-Messages kopieren; Tippfehler-Korrekturen und reine Merges weglassen. `CHANGELOG.md` steht in `exclude` und wird nicht ausgeliefert.

## Abhängigkeiten

Ziel: kein Abhängigkeits-Wildwuchs. Jede Abhängigkeit ist **genau dokumentiert** – so, dass jemand ohne Vorwissen sie nachvollziehen, aktualisieren oder wieder entfernen kann.

- **Alles steht in `DEPENDENCIES.md`, bevor es benutzt wird:** Bibliotheken im Browser, Gems, npm-Pakete und `npx`-Werkzeuge, GitHub Actions, Schriften, lokale Werkzeuge der Skripte (Python-Pakete, Chrome, OpenSCAD …). Was dort nicht steht, wird nicht benutzt – keine Abhängigkeit „nebenbei“.
- **Pro Eintrag:** Zweck (wofür, was ohne sie fehlt) · **genaue Version** (keine Bereiche, kein `latest`; wo das noch nicht geht, als offener Punkt markieren) · Herkunft (URL und der **exakte Befehl** zum Holen, Datum) · wo sie liegt bzw. festgelegt ist (Pfad, Workflow) · wer sie benutzt (Dateien) und wann sie geladen wird (immer / erst bei Bedarf / nur Build / nur lokal) · Lizenz · bei kopierten Dateien **SHA-256** · was geprüft wurde (lädt nichts von außen, keine Tracker, Größe) · Änderungen (am besten keine – sonst jede genau beschreiben) · wie man **aktualisiert** (Schritte und was danach zu testen ist) · wie man sie **entfernt** (was dann wegfällt, Rückfall).
- **Erst prüfen, ob es ohne geht.** Wenig eigener Code ist oft besser als eine Bibliothek (`karte.js`, `netzwerk.js`, `badge3d.js` kommen ohne aus).
- **Im Browser nur als unveränderte Kopie** in `assets/js/third-party/<name>/` mit `LICENSE` und `README.md` (dieselben Angaben in kurz), nie per CDN (Datenschutzversprechen im Impressum), erst bei Bedarf laden, ohne sie muss die Seite weiter funktionieren. Den Ordner nicht `vendor/` nennen – den ignorieren `.gitignore` und Jekyll.
- **Jede Änderung an Abhängigkeiten** (neu, Update, entfernt) zusätzlich mit genauer Version im `CHANGELOG.md` und in der PR-Beschreibung; `DEPENDENCIES.md` im selben Commit aktualisieren (auch das Datum „Stand“).
- **Offene Punkte** (z. B. nicht festgelegte Versionen) bleiben in `DEPENDENCIES.md` sichtbar, bis sie erledigt sind.

## GitHub Issues

**Aufgaben, Bugs und offene Punkte leben als GitHub Issues** (`gh issue …`) – nicht nur im Chat oder in Markdown-Dateien. So bleibt nichts liegen, wenn eine Sitzung endet, und alle sehen den Stand. Vorbild: #129 (Sammel-Issue „Direkt bearbeiten“).

- **Bugs aus der Claude-CLI melden:** Meldet Falko einen Fehler oder Wunsch in einer Sitzung („das geht nicht“, „wir sollten …“), sofort ein Issue anlegen – vorher mit `gh issue list --search "…"` nach einem passenden suchen und dann lieber das bestehende ergänzen. Inhalt auf Deutsch: was passiert, was erwartet war, Schritte zum Nachstellen, Seite/Adresse, Screenshot oder Link zum fehlgeschlagenen Workflow; Label `bug` bzw. `enhancement`.
- **Beim Arbeiten an einem Issue** es aktuell halten: zu Beginn kurz kommentieren (Branch/PR), Checkboxen abhaken, sobald etwas erledigt ist, neue Erkenntnisse und Teilaufgaben ergänzen. Die PR-Beschreibung verweist darauf („Teil von #N“, oder „Closes #N“, wenn der PR es ganz erledigt).
- **Erledigtes schließen** – mit einem Kommentar, was wo erledigt wurde (PR-Nummern); Reste in ein bestehendes oder neues Issue übertragen und verlinken.
- **Sitzung beenden:** Alles, was offen bleibt (auch Ideen und Entscheidungen, die noch anstehen), steht danach in einem Issue. Markdown-Pläne im Repo (z. B. `PLAN_DIRECT_EDITING.md`, `EDITING_CONFLICTS.md`) bleiben die ausführliche Beschreibung; das Issue ist die Aufgabenliste und verlinkt sie.
- **Größere Brocken** als eigenes Issue abspalten und im Sammel-Issue verlinken; Einstellungen, die nur Falko ändern kann (Branch-Schutz, Collaborators), als solche kennzeichnen.
- Keine nackten `@namen` in Issues (GitHub benachrichtigt sonst echte Accounts) – Rollen oder Code-Schreibweise nutzen.

## Branches und Pull Requests

**Jede Sitzung bekommt einen eigenen Pull Request.** Falko arbeitet nicht Vollzeit an der Seite; Worktrees und Claude-Sitzungen gehen zwischendurch verloren. Deshalb jede Sitzung (jeden Auftrag) sofort in einem eigenen Worktree auf einem neuen Branch von `origin/main` beginnen und, sobald es eine erste Änderung gibt, committen, pushen und einen Pull Request öffnen (bei Unfertigem als Draft mit `gh pr create --draft`). Nie Änderungen nur unkommittiert im Haupt-Checkout oder in einem Worktree liegen lassen – am Ende der Sitzung muss alles in einem PR stehen. Folgeaufträge in derselben Sitzung kommen in denselben PR.

Wer einen Branch pusht (nicht `main`), öffnet dazu immer einen Pull Request mit `gh pr create` – auf Deutsch und mit Vorschaubildern:

1. `bundle exec jekyll build`, dann Screenshots der betroffenen Seiten:
   `python3 -I _scripts/pr_vorschau.py /pfad/der/seite/ …` (Seitenanfang) oder mit `--unten` (Ausschnitt über dem Footer, z. B. für Änderungen am Seitenende). Das Skript nimmt Desktop (1280 px) und Handy (390 px) mit Headless-Chrome auf, lädt die Bilder auf den Branch `pr-previews` (Ordner = Branchname, nie in den Feature-Branch) und gibt eine Markdown-Tabelle für die PR-Beschreibung aus.
2. Bilder vor dem Hochladen selbst ansehen (`--nur-lokal` speichert nur nach `_pr-vorschau/`, in `.gitignore`). Es gelten dieselben Regeln wie auf der Seite: keine erkennbaren Kindergesichter, keine Kennzeichen, Namen oder Zugangscodes.
3. PR-Beschreibung: **Was** sich ändert, **warum**, **wie geprüft**, zugehöriges Issue („Teil von #N“ / „Closes #N“) (Build, Link-Check, angesehene Seiten), dann die Vorschau-Tabelle. Titel wie die Commit-Message; die Makespace-Regel gilt auch hier.
4. Bei Inhaltsänderungen reicht ein Screenshot der geänderten Seite. Ohne sichtbare Änderung (Workflow, Skripte) keine Vorschau – dann kurz sagen, warum.
