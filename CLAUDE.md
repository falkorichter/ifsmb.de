# CLAUDE.md — ifsmb.de

Website des „Institut für spontane Makespace Buildung“. Jekyll 4, GitHub Pages, Custom Domain `ifsmb.de`.

## Build

```bash
bundle exec jekyll build    # → _site/
bundle exec jekyll serve    # http://localhost:4000
ruby _scripts/check_site.rb # nach dem Build: tote Links, verwaiste Seiten, Geokoordinaten (--extern: externe Links)
ruby _scripts/check_galerien.rb # Galerien müssen Markdown sein (keine HTML-Galerien)
ruby _scripts/check_geodaten.rb # Fotos dürfen keine Geokoordinaten (EXIF-GPS/XMP) enthalten
ruby _scripts/test_formulare.rb # Formulare (➕, Todos) ↔ Vorlagen ↔ Pages CMS (.pages.yml); braucht Node
ruby _scripts/test_i18n.rb      # nach dem Build: Texte der Bedienung in de/en/fr vollständig, Schlüssel in _site vorhanden
node _scripts/test_merge.js     # Dreiwege-Zusammenführung (assets/js/merge.js) für Konflikte beim direkten Bearbeiten
_scripts/test_e2e.sh            # E2E: ➕/✏️-Formulare mit GitHub-Verbindung in Headless-Chrome gegen ein Fake-GitHub (baut vorher; --no-build)
```

**E2E-Tests** (`_tests/e2e/`, Anleitung in `_tests/e2e/README.md`): `node --test` + Chrome über das DevTools-Protokoll, keine npm-Pakete (Node ≥ 22, Chrome – siehe `DEPENDENCIES.md`). Das Fake-GitHub (`_tests/e2e/lib/fake-github.js`) hält Git und Pull Requests im Speicher und hat eine Steuer-API (`/__fake/…`) für Szenarien (fremde Commits, PRs öffnen/mergen/schließen, abgelaufene Tokens, Fehler einschleusen). `assets/js/github-api.js` nimmt die Fake-Adresse aus `localStorage["ifsmb-github-api"]` nur auf `localhost`/`127.0.0.1`. Wer an `neu.js`, `formular.js`, `github-api.js`, `photo-editor.js` oder `edit-buttons.html` arbeitet, lässt sie laufen und ergänzt Szenarien; in CI läuft `.github/workflows/e2e.yml`.

Nach neuen Seiten/Posts den Link-Check laufen lassen; er läuft auch im Pages-Workflow und stoppt das Deployment bei Fehlern. Externe Links, die dauerhaft tot sind, nicht löschen, sondern in Markdown mit `{: .link-tot}` hinter dem Link markieren (`[Text](url){: .link-tot}`): Das Layout hängt 🪦 an und erklärt das Symbol unten auf der Seite; `--extern` prüft markierte Links nicht mehr. Private Repos („noch privat“) nicht markieren. Das gilt nur für Links, die früher funktioniert haben (ältere Beiträge, übernommene Texte) – einen frisch recherchierten Link, der schon beim Einfügen tot ist, einfach entfernen.

Ruby 3.1.2 (`.ruby-version`). `_site/` niemals committen.

## Sprache

Alle sichtbaren Texte sind **Deutsch**. Ausnahme: Die **Bedienung** (Menüs, Footer, Knöpfe, Überschriften und Hinweise aus Layouts/Includes, Status-Abzeichen, Texte aus JS) gibt es zusätzlich auf Englisch und Französisch – die Inhalte bleiben deutsch. Alle Texte der Bedienung stehen in `_data/i18n/de.yml`, `en.yml`, `fr.yml` (Schlüssel englisch, in allen drei Dateien gleich). **Neuer Text in einer Vorlage:** in alle drei Dateien eintragen und als `<span data-i18n="bereich.schluessel">{{ "bereich.schluessel" | t }}</span>` schreiben (Attribute: `data-i18n-attr="title:schlüssel"`, Parameter: `{{ "schlüssel" | t: "n", 3 }}` plus `data-i18n-params="{{ "n" | i18n_params: 3 }}"`, Text mit Link/Code: `t_html`, Datum: `{{ date | i18n_date }}` – siehe `_plugins/i18n.rb`); in JS `I18n.t("schlüssel", { … })` mit deutschem Rückfall (`Formular.t`). Übersichtsseiten können Titel und Lead mit `i18n_title`/`i18n_lead` übersetzen; Inhalte (Front Matter, Markdown) nie. Englisch und Französisch natürlich formulieren, nicht Wort für Wort; im Französischen geschütztes Leerzeichen vor `: ? !`. `ruby _scripts/test_i18n.rb` prüft das. Umschalter, Erkennung und `localStorage["ifsmb-language"]`: `assets/js/i18n.js`, im Impressum unter Datenschutz beschrieben.

**Quellcode ist Englisch** – Ordner- und Dateinamen, Bezeichner (Funktionen, Variablen, CSS-Klassen, IDs, localStorage-Schlüssel, Parameter von Includes) und Code-Kommentare in Skripten, Workflows, Plugins, Layouts/Includes (Liquid- und HTML-Kommentare), CSS und JS, auch Docstrings. Neue Ordner heißen z. B. `assets/js/third-party/`, nicht `bibliotheken/`; Dokumente im Repo ebenso (`DEPENDENCIES.md`). **Nur Inhalte dürfen deutsch (oder in einer anderen Sprache) heißen:** Beiträge, Termine, Projekte, Seiten und ihre Adressen, die Ordner ihrer Bilder (`assets/images/news/<slug>/`). Die **Felder im Front Matter** (`linked`, `personal`, `location`, `part_of` …), die Felder der Todo-Dateien und die Dateinamen und Schlüssel in `_data/` sind dagegen Quelltext und englisch; nur ihre Werte (Texte, Namen, `status: abgeschlossen`, `kind: frage` …) bleiben deutsch. **Dokumentation ist (vorerst) deutsch:** Der Inhalt von `CLAUDE.md`, `CHANGELOG.md`, `DATA_STRUCTURES.md`, `DEPENDENCIES.md`, READMEs und PR-Beschreibungen bleibt deutsch – nur die Dateinamen sind englisch. Später kann die Dokumentation auf Englisch umgestellt oder übersetzt werden. Ältere deutsche Namen im Code (z. B. `neu.js`, `formular.js`, `_plugins/einzeldateien.rb`, Funktionen wie `baueFelder`) nicht nebenbei umbenennen – das ist eine eigene Aufräumarbeit mit eigenem PR; neuer Code daneben bekommt trotzdem englische Namen. Deutsch bleibt alles, was Besucher*innen oder Redakteur*innen sehen: Seitentexte, Fehlermeldungen und Hilfetexte von Skripten, Namen von Workflow-Schritten, Commit-Messages und PR-Beschreibungen.

Immer **Makespace** schreiben, nie „Makerspace“. Grund: „Maker“ ist im Deutschen ein männliches Wort, und wir wollen die Gender-Diskussion vermeiden. Das gilt für alle Texte: Seiten, Posts, Projekte, Profile, Meta-Beschreibungen, Alt-Texte und Commit-Messages.

## Struktur

- `_posts/` Neuigkeiten (`/news/`)
- `_team/` Collection, ein Profil pro Datei (`/team/:name/`), Layout `member`; mit `not_in_team: true` bekommt eine Person eine eigene Seite unter `/team/:name/` und kann überall verlinkt werden (`team`, `author`, `owner_team`, `linked`), erscheint aber nicht in der Übersicht auf `/team/`; Fremdfotos (Presse, Agentur) nur mit Erlaubnis und mit Bildnachweis in `photo_credit` (erscheint unter dem Namen)
- `_projects/` Collection (`/projects/:name/`), Layout `project`; `status: abgeschlossen` → Archiv `/projects/archive/`; `status: idee` = Projektidee (eigener Abschnitt „Ideen“, nicht auf der Startseite); `status: anfrage` = eingegangene Anfrage, die vielleicht ein Projekt wird (eigener Abschnitt „Anfragen“, nicht auf der Startseite). **Teilprojekte:** `part_of: [<Dateiname des übergeordneten Projekts>, …]` (z. B. `[3d-druck-ag-ktg]`; ein einzelner Name ohne Liste geht auch) – ein Teilprojekt kann zu mehreren Projekten gehören und erscheint dann auf jeder Elternseite unter „Teilprojekte“, aber nicht in den Übersichten (Startseite, `/projects/`, Archiv); sie zeigen oben und unten „Dieses Projekt ist ein Teil von: …“. **Verwandte Projekte:** `related: [<Dateiname>, …]` zeigt unten Buttons „Verwandte Projekte“ – in beide Richtungen, ein Eintrag bei einem der Projekte reicht; und haben ein eigenes `event_tag`. `start` muss immer ein Datum sein (wird zum Sortieren genutzt), `event_tag` ein eigenes Stichwort – nie ein allgemeines wie `35services`, sonst landen alle Beiträge dazu auf der Projektseite; `event_tag: ktg` listet alle Termine und Posts mit `tags: [ktg]` auf der Projektseite, und die Terminseite verlinkt zurück aufs Projekt. Fortschritt bevorzugt als **kleine Beiträge** (Posts mit dem `event_tag` des Projekts in `tags`, persönliche mit `personal: true`; mit `project_only: true` erscheint ein Beitrag nicht unter Neuigkeiten, auf der Startseite und im RSS-Feed, sondern nur auf der Projektseite) – so kann jede*r Beteiligte eigene Updates schreiben. Fotos und Videos dürfen auch direkt auf die Projektseite (als Markdown-Galerie im Text, siehe „Bilder und Videos“), vor allem bei einfachen Projekten mit wenigen Bildern; zeigen sie einen bestimmten Fortschritt oder Tag, lieber als Beitrag. Kurze Notizen ohne eigenen Beitrag als `updates:` (Liste aus `date` und `text` in Markdown, ohne Liquid). Die Projektseite mischt beides zu „Stand / Updates“ (neuestes zuerst, mit Autor*in); „Letztes Update“ im Kopf und auf der Projektkarte kommt aus `_includes/projekt-letztes-update.html`; Projektkarten in den Übersichten kommen aus `_includes/projekt-karte.html` und zeigen mit `_includes/projekt-aktivitaet.html` Symbole mit hochgestellten Zahlen (Teilprojekte, Termine, Updates, Geräte, Beteiligte) als Direktlinks in die Projektseite; Beiträge zeigen oben „Update zum Projekt …“
- `_challenges/` Collection (`/challenges/:name/`), Layout `herausforderung`: Aufgaben, Probleme und offene Fragen – kleiner als ein Projekt; **ein Projekt hat viele Herausforderungen**. Felder: `kind` (`aufgabe`/`problem`/`frage`), `status` (`offen` – Standard, `in-arbeit`, `geloest`), `since`, `solved_on`, `solution` (Markdown, erscheint unter „Lösung“), `team` (Zuständige, eine oder mehrere Personen), `projects` (Projekt-Dateinamen; alternativ `tags` mit dem `event_tag` des Projekts), `linked` (Termine, Geräte, Beiträge, Partnerseiten …), `personal: true` (aus privaten Projekten: eigener Abschnitt auf der Übersicht). Projektseiten zeigen ihre Herausforderungen als Karten (`#herausforderungen`, offene zuerst), Projektkarten zählen offene mit 🧗, Teamprofile listen die eigenen; sonst erscheinen sie unten bei „Verbindungen“. Karte und Status kommen aus `_includes/herausforderung-karte.html` und `_includes/herausforderung-status.html`. Offene Fragen in Projekttexten („Welche Teile fehlen?“) lieber als Herausforderung anlegen statt als Teilprojekt.
- `_data/partners.yml` Partnerliste – neue Partner gehen auch als eigene Datei `_data/partner/<name>.yml` (gleiche Felder, ein Partner pro Datei; `_plugins/einzeldateien.rb` hängt sie an die Liste an, „➕ Partner“ auf `/partners/` legt so eine Datei an); `logo_dark: true` für helle Logos; `page: /partners/<name>/` verlinkt eine eigene Partnerseite (`partners/<name>/index.md`); **Partner ohne eigene Seite bekommen automatisch eine** unter `/partners/<slug>/` (`_plugins/partner_pages.rb` + `_includes/partner-seite.html`: Logo, Beschreibung, Website, Geräte und „Verbindungen“; `page` wird dafür gesetzt, ✏️ öffnet die Datendatei); die Partnerübersicht listet automatisch alle Projekte, deren `partners:` den Namen enthält (persönliche mit Hinweis), und die Geräte mit `owner_partner`
- `_events/` Kalender-Termine (`/calendar/:name/`), Layout `event`; Felder `start`, `end`, `all_day`, `location`, `location_url`, `summary`, `team` (Team-Kürzel der Leute, die dabei sind/waren → Teamprofil „Termine“, nur eintragen, wer wirklich da war), optional `gallery` (Liste aus `image`, `thumb`, `alt`; Bilder unter `assets/images/kalender/<termin>/`, Originale in `_logo/kalender/` – nicht committet) `date_label` (Text statt Datum, wenn der Tag noch nicht feststeht – iCal macht daraus einen ganztägigen Termin am Ersten des `start`-Monats mit „TBD: “ vor dem Titel) `projects` (Liste von Projekt-Dateinamen – zusätzlich zu Projekten, deren `event_tag` in `tags` steht), `partners` (Namen aus `_data/partners.yml`, erscheinen auf `/partners/`), `personal: true` (private Termine aus dem Team, brauchen `team`: nie auf Startseite, in `/calendar/` oder im iCal-Feed, nur im Teamprofil und auf der Terminseite mit Hinweis „kein Termin des Instituts“) und `project_only: true` (interne Termine, z. B. Ausflüge der KTG-AG: solange sie bevorstehen, nicht auf der Startseite, im Kalender und im iCal-Feed, nur auf der Projektseite über das Stichwort und auf der Terminseite selbst; danach ganz normal unter „Vergangene Termine“ – der Kalender wird bei jedem Build neu berechnet)
- `_data/slogans.yml` wechselnde Slogans auf der Startseite (`text`: jede Zeile eine Zeile auf der Seite, `**fett**` = gelb hervorgehoben; der erste steht ohne JavaScript da) – neue Slogans einfach unten anhängen, auch in Pages CMS; Besucher*innen schlagen welche über `{% include slogan-editor.html %}` vor (Beitrag „Slogans gesucht“), die Datei liegt dafür unter `/source/_data/slogans.yml`
- `calendar.ics` erzeugt den iCal-Feed `/calendar.ics` (die alte Adresse `/kalender.ics` liefert `_plugins/alte_adressen.rb` weiter als Kopie aus). Die Datei enthält echte CRLF-Zeilenenden (RFC 5545) – nur mit Werkzeugen bearbeiten, die `\r\n` erhalten (`.gitattributes`: `-text`). Lange Zeilen bricht `_includes/ics-line.txt` um. Kopf und VEVENT stehen in `_includes/ics-kopf.txt` und `_includes/ics-vevent.txt`; dieselben Bausteine nutzt `_plugins/termin_ics.rb`, das pro Termin eine eigene Datei `/calendar/<termin>.ics` erzeugt und pro Projekt, Teamprofil und Partnerseite einen Feed mit allen Terminen, auch vergangenen (`/projects/<name>.ics`, `/team/<name>.ics`, `/partners/<name>.ics`). Die Buttons dazu („📅 In den Kalender“ auf der Terminseite, „📅 Abonnieren“ neben der Termine-Überschrift auf `/calendar/`, Projekt, Teamprofil, Partnerseite) kommen aus `_includes/kalender-abo.html`: ein Fenster (`<dialog id="abonnieren">`, Skript `assets/js/abo.js`, ohne JS ein normaler Link zur `.ics`) mit „Apple Kalender & Outlook“ (`webcal://` bzw. die `.ics` eines Termins), „Google Kalender“ (Abo-Link `calendar.google.com/calendar/render?cid=webcal://…` bzw. ausgefülltes Formular `action=TEMPLATE`) und Download. Ein Kalender-Fenster pro Seite; `<seite>#abonnieren` öffnet es direkt. Welche Termine dazugehören, entscheidet `_includes/termine-auswahl.html` – für Seite und Feed gleich.
- **RSS-/Atom-Feeds**: `/feed.xml` (Neuigkeiten des Instituts, ohne `personal`/`project_only`) und aus `_plugins/beitrag_feeds.rb` pro Projekt `/projects/<name>/feed.xml` (Beiträge mit dem `event_tag` plus die `updates:` – wie „Stand / Updates“), pro Person `/team/<name>/feed.xml` (alle Beiträge mit ihr als `author`, auch persönliche) und `/news/personal/feed.xml`. Alle Feeds nutzen `_includes/atom-feed.xml`, die Auswahl für Projekte/Personen steht in `_includes/feed-auswahl.html` (für Seite und Feed gleich). Die Buttons „📡 RSS-Feed“ (auf `/news/`, `/news/personal/`, neben „Stand / Updates“ auf Projektseiten, im Kopf des Teamprofils) kommen aus `_includes/feed-abo.html`: ein Fenster wie beim Kalender (`<dialog id="rss">`, `<seite>#rss` öffnet es) mit Feed-Adresse zum Kopieren, „Im Feed-Reader öffnen“ (`feed:`), Feedly und Inoreader.
- `_press/` Pressemitteilungen (`/press/:slug/`), Layout `press`; Kurzprofil & Pressekontakt in `_data/press.yml`, Downloads in `_data/press_kit.yml`, Berichte anderer über uns („Wir in der Presse“) in `_data/press_reports.yml` oder als eigene Datei `_data/press_report/<name>.yml` (wird nach `date` einsortiert; „➕ Wir in der Presse“ auf `/press/`)
- Posts mit `original_url` / `original_site` / `author` (Team-Kürzel) zeigen automatisch den Hinweis „Ursprünglich veröffentlicht von … auf …“
- `_equipment/` Ausstattung (`/equipment/:name/`), Layout `equipment`. Das Institut besitzt (noch) nichts: jedes Gerät hat mindestens einen Besitz-Eintrag: `owner_partner` (Namen aus `_data/partners.yml`), `owner_team` (Team-Kürzel), `owner_name` (freie Namen) – jeweils ein Wert oder eine Liste, kombinierbar (mehrere Besitzer*innen). Besitz und Standort sind besondere Verbindungen: eigene Gruppen „Gehört“/„Standort“ unten auf der Geräteseite, eigene Linien im Netzwerk (`/network/`); `location` ohne `location_partner` wird dort ein eigener Ort. `status:` `in-aussicht` (kommt vielleicht), `in-reparatur`, `im-test`. Standort mit `location` (Text) und optional `location_partner` (Partnername → Link). Weitere Fotos als `gallery` (Liste aus `image`, `thumb`, `alt`), Videos als `videos` (Liste aus `src`, `poster`, `caption`). Neuigkeiten zum Gerät (Umbauten, Erfahrungen, Reparaturen) als `updates:` (Liste aus `date` und `text` in Markdown, Fotos darin als Markdown-Galerie mit `{: .gallery}`) – erscheinen als „Stand / Updates“ auf der Geräteseite (neuestes zuerst), „Letztes Update“ steht im Kopf. Die Übersicht `/equipment/` gruppiert automatisch nach `category` (enthält „3D-Drucker“ / „3D-Scanner“ / Rest). Ohne freies Foto: eigene SVG-Illustration mit `image_is_illustration: true` – keine Hersteller- oder Shopfotos übernehmen (Urheberrecht). Partnerseite und Teamprofil listen die Geräte automatisch.
- **Stichworte (`tags`)** verknüpfen alles miteinander: Posts, Termine, Ausstattung, Pressemitteilungen tragen `tags: [...]`, Projekte ihr `event_tag`. Die Stichworte stehen oben auf der Seite, `/tags/` listet alle mit ihren Seiten. Anzeigenamen in `_data/tags.yml`. Eine eigene Liste „Verknüpft“ (alles mit gemeinsamen Stichworten) gibt es nicht mehr – die Zusammenhänge zeigt „Verbindungen“ (semantisch, über die Felder und das Projekt-Stichwort).
- Stichwort-Konventionen: Kleinbuchstaben mit Bindestrich. Projekt-Ort (`ktg`, `rosalind-franklin-gym`), Herkunft (`35services` für alle von 35services.de übernommenen Beiträge), Besitzer*in eines Geräts (`35services`, `bietenholz`), Gerät (`bambu-lab-a1-mini`, `waermebildkamera`, `u1` für den Snapmaker U1 …), Gerätetyp (`3d-drucker`).
- `/project/ideas/` (`project/ideas.md`): statische Seite, keine Collection – deshalb nicht unter `/projects/`; Linksammlung mit Projektideen; ✅ = schon gebaut. Links immer ohne Tracking-Parameter (`?si=`, `?is=`, `&pp=`, `spm=` …).
- `/angebot/`: Angebote und „Warum ein Institut?“
- **Persönliche Beiträge und Projekte** (`personal: true`): private Makespace-Updates aus dem Team. Sie erscheinen **nicht** in den Listen des Instituts (Neuigkeiten, Startseite, RSS, Projekte, Archiv), sondern im Teamprofil („Persönliche Projekte“, „Persönlicher Blog“) und auf `/projects/personal/` bzw. `/news/personal/` (unten auf den Listenseiten verlinkt). Posts brauchen `author` (ein Team-Kürzel oder eine Liste bei mehreren Autor*innen – der Beitrag erscheint dann in jedem persönlichen Blog), Projekte die Person unter `team`. Die Seiten tragen den Hinweis „kein Beitrag/Projekt des Instituts“.
- Navigation steht in `_config.yml` unter `nav`; Einträge mit `children` werden zu einem Untermenü (z. B. „Wir“ mit Projekte, Angebot, Ausstattung, Team)
- `future: true` in `_config.yml`, sonst baut Jekyll Termine mit Datum in der Zukunft nicht
- **Suche** `/search/` mit Pagefind: Index entsteht erst nach `jekyll build` im Workflow `.github/workflows/pages.yml` (`npx pagefind --site _site`; Pages-Source = „GitHub Actions“). Indexiert wird alles im `data-pagefind-body`-Wrapper aus `_layouts/default.html`, Filter „Bereich“/„Stichwort“ aus `_includes/suche-meta.html`. Reine Übersichtsseiten bekommen `search: false`. Pagefind-Version im README und Workflow gleich halten. **Suchindex zum Finden von Erwähnungen nutzen:** Um bei neuen Personen, Projekten, Geräten oder Themen alle passenden Stellen auf der Website zu finden (und nichts zu übersehen, z. B. abweichende Schreibweisen oder Übersichtsseiten wie `/spenden/`), den lokalen Server starten, den Pagefind-Index mit `npx -y pagefind@1.5.2 --site _site` bauen und direkt per Node abfragen (`const pf = await import("./_site/pagefind/pagefind.js"); await pf.options({ basePath: "http://127.0.0.1:<port>/pagefind/" }); await pf.init(); const res = await pf.search("Suchbegriff");`), zusätzlich zu `/search/index.json` (`search/index.json`; früher `todos/suchindex.json` – als eine Datei für Föderation gedacht und auf `/search/` verlinkt).
- **Bearbeiten-Button**: `_layouts/default.html` zeigt unter jeder Seite einen Button „✏️ `<page.path>`“ (der Pfad der Quelldatei) → GitHub-Editor für `page.path` (Repo/Branch in `_config.yml` unter `repository`/`branch`)
- **Neu-Buttons**: In derselben Zeile wie der Bearbeiten-Button stehen ➕-Buttons (`_includes/neu-buttons.html`), die den GitHub-Editor für eine neue Datei öffnen (`/new/<branch>/<ordner>?filename=…&value=…`) – mit einer Vorlage aus `_includes/vorlagen/` (Beitrag, Termin, Projekt, vergangenes Projekt fürs Archiv, Gerät, Herausforderung, Teamprofil, Pressemitteilung, Partner, Pressebericht), die alle Felder mit Kommentar enthält und die Verbindung zur aktuellen Seite schon eingetragen hat (Teamprofil → `author`/`team`/`owner_team`, Projekt → `event_tag`/`part_of`, Partnerseite → `partners`/`owner_partner`, Termin/Gerät/Beitrag → `tags` + `linked`, Projekt/Termin/Teamprofil → Herausforderung mit `projects`/`team`; Übersichtsseiten → leere Vorlage; `/projects/archive/` → vergangenes Projekt mit `status: abgeschlossen` und Gliederung für den Rückblick). `part_of` bleibt in den Vorlagen leer (nil), sonst verschwindet ein Projekt aus den Übersichten – die filtern auf `part_of == nil`. `JJJJ-MM-TT`, `JJJJ` und `TZTZ` ersetzt ein kleines Skript beim Klick durch das heutige Datum. **Ein normaler Klick öffnet stattdessen ein Formular auf der Seite** (`assets/js/neu.js`, erst beim Klick geladen; Strg/⌘-Klick und „Vorlage mit allen Feldern ↗“ öffnen weiter GitHub direkt): Felder mit Auswahllisten und Autovervollständigung, Live-Vorschau der Datei, Entwurf im localStorage, „Auf GitHub anlegen“ kopiert die Datei und öffnet den GitHub-Editor mit dem fertigen Inhalt. Jeder Typ ist ein Schema in `TYPEN` (`neu.js`); die Verbindung zur Seite kommt aus `data-neu` (`_includes/neu-button.html`). Bausteine, die auch der Todo-Editor nutzt (Dialog, Chip-Felder mit Autovervollständigung, Personen-Avatare, YAML, GitHub-Schritt), stehen in `assets/js/formular.js`; Konfiguration und Skript-Lader in `_includes/formular-config.html` (in jeder Seite), Daten aus `/search/index.json` (`search/index.json`) (Personen, Projekte, Stichworte, Partner, Gerätekategorien, Seiten). **Neues Feld oder neuer Typ:** Schema in `neu.js`, Vorlage in `_includes/vorlagen/` und `.pages.yml` gemeinsam ändern – `ruby _scripts/test_formulare.rb` (läuft in „Prüfen“ und „Pages“) prüft, dass jede Datei, die ein Formular schreibt, als YAML lesbar ist, nur Felder der Vorlage nutzt und zu Pages CMS passt (Ordner, Dateiname, Listen vs. Einzelwerte, Auswahlwerte, Datumsformat), und dass Todo-Dateien beim Lesen und Schreiben gleich bleiben. ## Konventionen

- Kein CSS-/JS-Framework, alle Styles in `assets/css/style.css` mit CSS-Variablen
- **Keine Namen der Seite im Code**: Layouts, Includes, Plugins, Skripte, JS und CSS nennen weder das Institut noch ifsmb.de, `falkorichter/ifsmb.de` oder Personen – damit eine andere Instanz (z. B. [35services.ifsmb.de](https://35services.ifsmb.de/)) denselben Code ohne Änderungen nutzen kann. Stattdessen `_config.yml`: `title`, `short_title` (Logo-Kürzel, Kalendernamen, Badge), `brand_name` (Text neben dem Logo, HTML erlaubt), `url` (Host für Link-Check, Formulare, Commit-Texte), `repository`, `contact_name` (wer Videos bekommt). JavaScript bekommt diese Werte und die Theme-Liste über `site`/`themes` in `_includes/formular-config.html`. Ausnahmen: technische Schlüssel wie `localStorage["ifsmb-theme"]` (gelten nur für die eigene Domain; umbenennen würde gespeicherte Wahl und Logins löschen), Code-Kommentare und Testdaten. Texte der Bedienung mit „Institut“ in `_data/i18n/` sind Daten, nicht Code.
- **Instanz-eigene Texte und Daten: `_data/instanz/`** (`_plugins/instanz.rb`): liegt Schlüssel für Schlüssel über `_data/` – `_data/instanz/i18n/de.yml` überschreibt nur die Texte darin (z. B. `footer.disclaimer`), `_data/instanz/<name>.yml` ersetzt Listen bzw. ergänzt Hashes in `_data/<name>.yml`. Die gemeinsamen Dateien bleiben so in allen Instanzen gleich, ein Abgleich mit ifsmb.de gibt dort keine Konflikte. Ein überschriebener i18n-Schlüssel muss in `_data/i18n/` existieren und dieselben Platzhalter haben, sonst bricht der Build ab; auch `assets/js/i18n-strings.js` und `test_i18n.rb` nehmen die Überschreibungen. ifsmb.de selbst hat kein `_data/instanz/`. Tests: `ruby _scripts/test_instanz.rb` (läuft in „Prüfen“).
- **Links auf Seiten, die nicht jede Instanz hat**, in Layouts und Includes in `{% ifpage /adresse/ %}…{% endifpage %}` (Gegenteil: `{% unlesspage %}`) – z. B. Spenden, Angebot, Impressum, Maschinenlesbar, Todos, Stichworte, Zurück-Links der Übersichten. Fehlt die Seite, fällt der Link weg statt ins Leere zu führen.
- Keine externen Ressourcen (Fonts, Skripte, Tracker) einbinden – Datenschutzhinweis im Impressum verspricht das. Ausnahmen, beide nur nach einem Klick und im Impressum unter Datenschutz beschrieben: die Kartenbilder von OpenStreetMap auf `/map/` („Karte laden“) und die Daten verbundener Instanzen auf `/network/` und `/search/` („🌐 Verbundene Instanzen einbeziehen“, siehe Föderation)
- Fremde Bibliotheken, Werkzeuge und andere Abhängigkeiten: siehe Abschnitt **„Abhängigkeiten“** unten und `DEPENDENCIES.md`. ## Beiträge von 35services.de übernehmen

Falko schreibt Beiträge zuerst auf https://35services.de. Soll ein Beitrag hier erscheinen, gilt dieses Muster:

1. **Datum & Titel** aus der WordPress-API holen (genaue Veröffentlichungszeit):
   `curl -s "https://35services.de/wp-json/wp/v2/posts?slug=<slug>&_fields=slug,date,title"`
   → Datei `_posts/<YYYY-MM-DD>-<slug>.md`, `date: <YYYY-MM-DD HH:MM:SS> +0100/+0200` (MEZ/MESZ beachten)

   ```yaml
   title: "<Titel wie im Original>"
   date: 2026-05-25 14:37:44 +0200
   author: falko-richter
   original_url: https://35services.de/<jahr>/<slug>/
   original_site: 35services.de
   ```
   Zusätzlich immer `tags: [35services]` setzen (plus Stichworte für erwähnte Geräte/Projekte).
   Das Layout `post` zeigt daraus oben automatisch „Ursprünglich veröffentlicht von Falko Richter auf 35services.de“ mit Link.
3. **Text** wörtlich übernehmen (Absätze, Listen, Links als Markdown). Einzige Änderung: „Makerspace“ → „Makespace“. E-Mail-Adressen nur in der schon verschleierten Form des Originals („falko [at] 35services [punkt] de“) oder per `.obf-mail`.
4. **Bilder** lokal speichern, nie von 35services.de einbinden: größte Version laden, mit Pillow ohne Metadaten neu speichern als `assets/images/news/<slug>/NN.jpg` (max. 1600 px) und `NN-600w.jpg`; einbinden als Markdown-Galerie (Bilder untereinander, darunter `{: .gallery}`, auch für ein Einzelbild). Aussagekräftige Alt-Texte, Screenshots beschreiben.
5. **Videos** (`wp-block-video`, oft 4K oder `.mov`) mit ffmpeg auf 720p verkleinern (`-crf 28 -preset slow -movflags +faststart -map_metadata -1`) nach `assets/video/news/<slug>/NN.mp4` plus Vorschaubild `NN.jpg`; einbinden als `![Beschreibung](/assets/video/news/<slug>/NN.mp4)` (eigener Absatz) an der Stelle wie im Original.
6. **YouTube** nie als iframe: Vorschaubild `img.youtube.com/vi/<id>/hqdefault.jpg` lokal speichern und als `<a class="video-link">` auf youtube.com verlinken.
7. Danach `bundle exec jekyll build`, Seite ansehen, Größe von `assets/` im Blick behalten.

## Durchsicht vor dem Push

- **Viele Änderungen auf einmal** (mehr als 2 betroffene Seiten/Ressourcen, z. B. mehrere Beiträge, Termine und Profile aus einer Nachricht): erst eine Durchsicht `_review.md` im Projektordner schreiben und **nicht pushen**, bis sie durchgesehen ist. Darin pro Änderung: was sich ändert, Link zur lokalen Seite, Annahmen und offene Fragen. Antworten werden direkt in die Datei geschrieben; nach dem Einarbeiten die Datei löschen. `_review.md` steht in `.gitignore` und wird nie committet.
- **Worktree live ansehen**: Wer in einem lokalen Worktree arbeitet (`.claude/worktrees/<name>/`), startet dort im Hintergrund einen eigenen Server, sobald es etwas zu sehen gibt – auf dem nächsten freien Port ab 4001 (Port 4000 gehört dem Haupt-Checkout; frei prüfen mit `lsof -nP -iTCP:<port> -sTCP:LISTEN`): `bundle exec jekyll serve --port <port>`. Die Adresse (`http://localhost:<port>/`) kommt mit klickbaren Links auf die geänderten Seiten in `_review.md` (im Worktree-Ordner) und in den Abschlussbericht, damit alles live angesehen werden kann; Port 4000 nur auf ausdrücklichen Wunsch auf den Worktree umstellen. Server laufen lassen, bis die Änderung gemergt oder verworfen ist.
- **Inline-Links auch semantisch verbinden**: Verlinkt ein Text eine andere Seite der Website (Projekt, Termin, Beitrag, Person, Gerät, Partner- oder normale Seite), die Verbindung zusätzlich im Front Matter eintragen (Ausnahme: `/network/` – dazu gehört ohnehin alles) – über das passende Feld (`tags`/`event_tag`, `team`, `partners`, `part_of` …) oder sonst `linked`. Dann erscheint sie unten bei „Verbindungen“ und im Netzwerk.
- **Inhaltsseiten in Markdown**: Texte als `.md` schreiben, HTML nur für Bausteine, die Markdown nicht kann (Karten-Raster, Hinweisboxen, verschleierte E-Mail) – darin mit `markdown="1"` weiter Markdown. Überschriften-Anker explizit setzen (`{: #anker}`), wenn andere Seiten darauf verlinken. Reine Listen-/Übersichtsseiten mit viel Liquid (Startseite, Kalender, Projekte …) bleiben HTML.
- **Links in Markdown immer klickbar**: als `[Text](URL)` schreiben, nie als nackte URL – das gilt für `_review.md`, Feedback-Dateien, PR-Beschreibungen und alle Inhalte.

## Changelog

`CHANGELOG.md` folgt [Keep a Changelog](https://keepachangelog.com/de/1.0.0/), auf Deutsch. **Nur Funktionen der Website kommen hinein** – neue oder geänderte Layouts, Includes, Plugins, Seitentypen und Felder, Skripte, Workflows, CSS/JS, Regeln für die Arbeit am Repo, behobene Fehler. **Keine Inhalte**: neue oder geänderte Beiträge, Termine, Projekte, Teamprofile, Geräte, Partner, Pressemitteilungen, Textseiten und Fotos bekommen keinen Eintrag – was wann dazukam, zeigen das Netzwerk und seine Zeitleiste (`/network/`). Jede nennenswerte Funktionsänderung kommt mit in den Commit: zuerst unter `## [Unreleased]`, sortiert nach `### Hinzugefügt`, `### Geändert`, `### Veraltet`, `### Entfernt`, `### Behoben`, `### Sicherheit`. Die Seite hat keine Versionsnummern: Beim Push nach `main` wird `[Unreleased]` zum Tagesabschnitt `## [JJJJ-MM-TT]` (neueste oben, Vergleichslinks unten pflegen). Einträge für Menschen schreiben, nicht Commit-Messages kopieren; Tippfehler-Korrekturen und reine Merges weglassen. `CHANGELOG.md` steht in `exclude` und wird nicht ausgeliefert.

## Abhängigkeiten

Ziel: kein Abhängigkeits-Wildwuchs. Jede Abhängigkeit ist **genau dokumentiert** – so, dass jemand ohne Vorwissen sie nachvollziehen, aktualisieren oder wieder entfernen kann.

- **Alles steht in `DEPENDENCIES.md`, bevor es benutzt wird:** Bibliotheken im Browser, Gems, npm-Pakete und `npx`-Werkzeuge, GitHub Actions, Schriften, lokale Werkzeuge der Skripte (Python-Pakete, Chrome, OpenSCAD …). Was dort nicht steht, wird nicht benutzt – keine Abhängigkeit „nebenbei“.
- **Pro Eintrag:** Zweck (wofür, was ohne sie fehlt) · **genaue Version** (keine Bereiche, kein `latest`; wo das noch nicht geht, als offener Punkt markieren) · Herkunft (URL und der **exakte Befehl** zum Holen, Datum) · wo sie liegt bzw. festgelegt ist (Pfad, Workflow) · wer sie benutzt (Dateien) und wann sie geladen wird (immer / erst bei Bedarf / nur Build / nur lokal) · Lizenz · bei kopierten Dateien **SHA-256** · was geprüft wurde (lädt nichts von außen, keine Tracker, Größe) · Änderungen (am besten keine – sonst jede genau beschreiben) · wie man **aktualisiert** (Schritte und was danach zu testen ist) · wie man sie **entfernt** (was dann wegfällt, Rückfall).
- **Erst prüfen, ob es ohne geht.** Wenig eigener Code ist oft besser als eine Bibliothek (`karte.js`, `netzwerk.js`, `badge3d.js` kommen ohne aus).
- **Im Browser nur als unveränderte Kopie** in `assets/js/third-party/<name>/` mit `LICENSE` und `README.md` (dieselben Angaben in kurz), nie per CDN (Datenschutzversprechen im Impressum), erst bei Bedarf laden, ohne sie muss die Seite weiter funktionieren. Den Ordner nicht `vendor/` nennen – den ignorieren `.gitignore` und Jekyll.
- **Jede Änderung an Abhängigkeiten** (neu, Update, entfernt) zusätzlich mit genauer Version im `CHANGELOG.md` und in der PR-Beschreibung; `DEPENDENCIES.md` im selben Commit aktualisieren (auch das Datum „Stand“).
- **Offene Punkte** (z. B. nicht festgelegte Versionen) bleiben in `DEPENDENCIES.md` sichtbar, bis sie erledigt sind.

## GitHub Issues

**Aufgaben, Bugs und offene Punkte leben als GitHub Issues** (`gh issue …`) – nicht nur im Chat oder in Markdown-Dateien. So bleibt nichts liegen, wenn eine Sitzung endet, und alle sehen den Stand. Vorbild: #129 (Sammel-Issue „Direkt bearbeiten“).

- **Bugs aus der Claude-CLI melden:** Meldet Falko einen Fehler oder Wunsch in einer Sitzung („das geht nicht“, „wir sollten …“), sofort ein Issue anlegen – vorher mit `gh issue list --search "…"` nach einem passenden suchen und dann lieber das bestehende ergänzen. Inhalt auf Deutsch: was passiert, was erwartet war, Schritte zum Nachstellen, Seite/Adresse, Screenshot oder Link zum fehlgeschlagenen Workflow; Label `bug` bzw. `enhancement`.
- **Beim Arbeiten an einem Issue** es aktuell halten: zu Beginn kurz kommentieren (Branch/PR), Checkboxen abhaken, sobald etwas erledigt ist, neue Erkenntnisse und Teilaufgaben ergänzen. Die PR-Beschreibung verweist darauf („Teil von #N“, oder „Closes #N“, wenn der PR es ganz erledigt).
- **Erledigtes schließen** – mit einem Kommentar, was wo erledigt wurde (PR-Nummern); Reste in ein bestehendes oder neues Issue übertragen und verlinken.
- **Sitzung beenden:** Alles, was offen bleibt (auch Ideen und Entscheidungen, die noch anstehen), steht danach in einem Issue. Markdown-Pläne im Repo (z. B. `PLAN_DIRECT_EDITING.md`, `EDITING_CONFLICTS.md`) bleiben die ausführliche Beschreibung; das Issue ist die Aufgabenliste und verlinkt sie.
- **Größere Brocken** als eigenes Issue abspalten und im Sammel-Issue verlinken; Einstellungen, die nur Falko ändern kann (Branch-Schutz, Collaborators), als solche kennzeichnen.
- Keine nackten `@namen` in Issues (GitHub benachrichtigt sonst echte Accounts) – Rollen oder Code-Schreibweise nutzen.

## Branches und Pull Requests

**Jede Sitzung bekommt einen eigenen Pull Request.** Falko arbeitet nicht Vollzeit an der Seite; Worktrees und Claude-Sitzungen gehen zwischendurch verloren. Deshalb jede Sitzung (jeden Auftrag) sofort in einem eigenen Worktree auf einem neuen Branch von `origin/main` beginnen und, sobald es eine erste Änderung gibt, committen, pushen und einen Pull Request öffnen (bei Unfertigem als Draft mit `gh pr create --draft`). Nie Änderungen nur unkommittiert im Haupt-Checkout oder in einem Worktree liegen lassen – am Ende der Sitzung muss alles in einem PR stehen. Folgeaufträge in derselben Sitzung kommen in denselben PR.

Wer einen Branch pusht (nicht `main`), öffnet dazu immer einen Pull Request mit `gh pr create` – auf Deutsch und mit Vorschaubildern:

1. `bundle exec jekyll build`, dann Screenshots der betroffenen Seiten:
   `python3 -I _scripts/pr_vorschau.py /pfad/der/seite/ …` (Seitenanfang) oder mit `--unten` (Ausschnitt über dem Footer, z. B. für Änderungen am Seitenende). Das Skript nimmt Desktop (1280 px) und Handy (390 px) mit Headless-Chrome auf, lädt die Bilder auf den Branch `pr-previews` (Ordner = Branchname, nie in den Feature-Branch) und gibt eine Markdown-Tabelle für die PR-Beschreibung aus. `pr-previews` ist ein reiner Bilder-Branch ohne gemeinsame Geschichte mit `main`: nie mergen, nie löschen (alte PR-Bilder hängen an seinen Commits), keinen PR dafür anlegen – GitHubs „Compare & pull request“-Hinweis danach ist normal (README, Abschnitt „Branch `pr-previews`“).
2. Bilder vor dem Hochladen selbst ansehen (`--nur-lokal` speichert nur nach `_pr-vorschau/`, in `.gitignore`). Es gelten dieselben Regeln wie auf der Seite: keine erkennbaren Kindergesichter, keine Kennzeichen, Namen oder Zugangscodes.
3. PR-Beschreibung: **Was** sich ändert, **warum**, **wie geprüft**, zugehöriges Issue („Teil von #N“ / „Closes #N“) (Build, Link-Check, angesehene Seiten), dann die Vorschau-Tabelle. Titel wie die Commit-Message; die Makespace-Regel gilt auch hier.
4. Bei Inhaltsänderungen reicht ein Screenshot der geänderten Seite. Ohne sichtbare Änderung (Workflow, Skripte) keine Vorschau – dann kurz sagen, warum.
